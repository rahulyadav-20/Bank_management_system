Part 1 Distributed Systems Foundations

Section 1 — Distributed Systems Foundations

1.1 Cluster Computing Architecture

A compute cluster is a collection of interconnected machines (nodes) that work together to solve computational problems that exceed the capacity of any single machine. Clusters are organized hierarchically:

  • Nodes: Individual servers with their own CPU, RAM, and local storage. A node runs one or more processes (JVMs in Spark's case).
  • Racks: Groups of 20–40 nodes sharing a top-of-rack (ToR) network switch. Intra-rack bandwidth is high (~10 Gbps); cross-rack bandwidth is lower.
  • Data Centers: Collections of racks connected via spine/leaf network fabric. A large Spark cluster may span hundreds of racks within a single data center.

The master-worker architecture pattern divides the cluster into a coordination node (master) that manages the workload and many worker nodes that execute tasks. In Spark:

  • The Driver acts as the master — it plans work and coordinates execution.
  • Executors are worker processes — they receive tasks, process data, and return results.
  • A Cluster Manager (YARN, K8s, Standalone) sits between them, allocating resources.

Spark's design assumes commodity hardware — standard, inexpensive servers rather than specialized high-end machines. This philosophy (inherited from Google's original MapReduce paper) means the system must tolerate frequent hardware failures. Spark handles this via RDD lineage-based recomputation rather than data replication.

Network topology awareness is critical for performance. Spark's scheduler is rack-aware: it prefers to place tasks on nodes where data already resides (PROCESS_LOCAL), then the same node (NODE_LOCAL), then the same rack (RACK_LOCAL), and only as a last resort sends data across racks (ANY). This minimizes the most expensive resource in distributed computing: network bandwidth.

1.2 Horizontal vs Vertical Scaling

Vertical scaling (scale-up) means adding more CPU, RAM, or disk to a single machine. It's simple but hits hard limits: you can't buy a 10,000-core single server. Cost increases superlinearly — a 2x more powerful server costs 4–10x more.

Horizontal scaling (scale-out) means adding more commodity machines to the cluster. This is the model Spark uses. Benefits include near-linear scalability, elasticity (add/remove nodes on demand in the cloud), and cost efficiency. The trade-off is coordination overhead: distributed systems must handle network communication, serialization, task scheduling, and failure recovery.

In cloud environments, Spark clusters leverage auto-scaling: worker pools grow during heavy ETL batches and shrink during off-peak hours, optimizing cost per compute-hour. Spark's Dynamic Allocation feature (`spark.dynamicAllocation.enabled=true`) adds or removes executors automatically based on pending task backlog.

Spark achieves linear horizontal scalability for most workloads: doubling executors roughly halves wall-clock time for embarrassingly parallel operations (map, filter). However, shuffle-heavy workloads (joins, aggregations) scale sub-linearly because of network overhead.

1.3 Shared-Nothing Architecture

In a shared-nothing architecture, each node owns its CPU, memory, and disk independently — no two nodes access the same memory or disk concurrently. This eliminates contention, locking, and coherence protocols that plague shared-memory (SMP) and shared-disk (Oracle RAC) architectures.

Spark implements shared-nothing via independent executor JVMs. Each executor has its own heap memory, its own BlockManager cache, and its own local disk storage. Executors never directly access another executor's memory — if data must move between executors, it goes through the shuffle (serialization → disk write → network transfer → deserialization).

The consequence is that data must be explicitly partitioned and moved between nodes during wide transformations (groupBy, join, repartition). This makes shuffle the most expensive operation in Spark — a direct consequence of the shared-nothing design.

1.4 Data Partitioning Strategies

🎯 Interview Tip Explain why hash partitioning causes skew on low-cardinality keys: if a column has only 3 values (e.g., a boolean True/False/Null), then hash(key) % 200 will produce only 3 distinct partition IDs — 197 partitions will be empty, and all data goes to 3 tasks. One value (e.g., "False" with 80% of rows) creates a massive skew task.

1.5 Data Locality

Data locality is the principle of scheduling computation where data already resides, avoiding expensive network transfers. Spark's scheduler implements this with a locality preference hierarchy:

Locality LevelData LocationPerformance
PROCESS_LOCALIn the same executor JVM's memory (BlockManager cache hit)Fastest — zero network I/O
NODE_LOCALOn disk on the same worker node (HDFS block)Fast — local disk read only
RACK_LOCALOn a different node in the same rackModerate — intra-rack network
NO_PREFData source has no locality preference (e.g., JDBC)N/A
ANYAnywhere in the clusterSlowest — cross-rack network

The scheduler waits up to spark.locality.wait (default 3 seconds) for a local slot before relaxing to the next level. In cloud environments with object storage (S3, GCS), data locality is largely lost — all reads are remote network calls regardless of which executor runs the task. This is why cloud Spark clusters depend on fast network fabric and data caching (e.g., Alluxio).

1.6 Fault Tolerance Mechanisms

Distributed systems must handle multiple failure modes:

  • Node crash: Executor JVM dies — partitions in memory are lost.
  • Network partition: Node becomes unreachable temporarily.
  • Straggler node: One node runs 10x slower due to hardware issues, noisy neighbor, or GC.
  • Process OOM: Executor runs out of heap — killed by JVM or container manager.

Spark uses lineage-based recomputation rather than data replication for fault tolerance. Every RDD/DataFrame tracks its lineage graph — the sequence of transformations from source data. If a partition is lost, Spark re-executes only the lineage of that specific partition from the closest available checkpoint or source. This avoids the 3x storage overhead of HDFS-style replication while maintaining fault tolerance for compute.

Checkpointing materializes a DataFrame/RDD to stable storage (HDFS/S3), truncating the lineage graph. This is critical for very long DAGs (e.g., iterative ML algorithms) where the lineage becomes deep enough that recomputation is prohibitively expensive. Streaming jobs also checkpoint state and offsets for exactly-once recovery.

Speculative execution (`spark.speculation=true`) detects straggler tasks (running significantly slower than their peers) and launches a duplicate task on a different executor. The first to finish wins, and the other is killed. This handles hardware-level stragglers but can cause duplicate writes for non-idempotent operations.

1.7 Replication Strategies

Full replication copies each data block to N nodes (HDFS default: 3 replicas). This provides high availability but triples storage cost. Erasure coding (available in HDFS 3.x) encodes data with parity blocks — provides redundancy at ~1.5x storage cost instead of 3x, but requires more CPU for encoding/decoding.

Spark itself does not replicate intermediate data by default. Shuffle files are written once to the local disk of the executor. If the executor dies, those shuffle files are lost, and the upstream stage must be re-executed. The External Shuffle Service (ESS) mitigates this by serving shuffle files from a separate long-lived process on each node.

1.8 Network Communication in Distributed Systems

Spark uses Netty for all network communication — a non-blocking, asynchronous RPC framework that handles thousands of concurrent connections efficiently. Network communication occurs in three main flows:

  • Control plane: Driver ↔ Executor heartbeats, task dispatch, status updates (small, frequent messages)
  • Shuffle data: Executor ↔ Executor block transfers during shuffle read (large, bulk data)
  • Broadcast: Driver → all Executors for broadcast variables (one-to-many, large payloads)

Serialization is the process of converting JVM objects to bytes for network transfer. Spark supports Java serialization (default, slow) and Kryo serialization (2–10x faster, requires class registration for best performance). The DataFrame/Tungsten engine uses its own binary format (UnsafeRow) that bypasses both.

⚙️ Engineering Insight Network is the #1 bottleneck in shuffle-heavy jobs. Key config: spark.rpc.message.maxSize (default 128 MB) controls max message size for RPC. spark.network.timeout (default 120s) controls when slow operations are considered failed. In large clusters, increase timeout to avoid false-positive failures during heavy shuffles.

1.9 CAP Theorem Basics

The CAP Theorem states that a distributed system can guarantee at most two of three properties simultaneously: Consistency, Availability, and Partition Tolerance. Since network partitions are unavoidable in real systems, the practical choice is between CP (consistent but may reject requests during partitions) and AP (available but may return stale data).

Apache Spark sits in the AP zone for batch processing: it prioritizes availability (tasks continue running on available nodes) and partition tolerance (task failures trigger lineage recomputation, not system shutdown). Consistency is eventual — data is consistent only after a job completes successfully.

For Structured Streaming, achieving exactly-once semantics requires additional coordination: idempotent sinks (Delta Lake), checkpoint-based offset tracking, and transactional writes — effectively adding a consistency layer on top of Spark's AP foundation.

Part 2 Introduction to Apache Spark

Section 2 — Introduction to Apache Spark

2.1 What Is Apache Spark?

Apache Spark is an open-source unified analytics engine for large-scale data processing. Its core innovation is an in-memory computation model: intermediate results between stages stay in RAM rather than being written to disk, eliminating the I/O bottleneck that crippled Hadoop MapReduce.

Spark is general-purpose — a single engine for batch ETL, real-time streaming, machine learning, graph processing, and SQL analytics. It offers a polyglot API: Scala (native JVM language), Java, Python (PySpark — the most popular), R (SparkR), and SQL.

2.2 History and Origin

  • 2009: Born at UC Berkeley AMPLab — Matei Zaharia's research project to address MapReduce limitations.
  • 2012: Foundational RDD paper published — "Resilient Distributed Datasets: A Fault-Tolerant Abstraction for In-Memory Cluster Computing".
  • 2013: Donated to Apache Software Foundation; Databricks founded as commercial steward.
  • 2014: Apache top-level project; set world record for large-scale sorting (100 TB in 23 minutes on 206 nodes).
  • 2016: Spark 2.0 — Structured APIs (DataFrame/Dataset), Tungsten engine, Catalyst optimizer matured.
  • 2020: Spark 3.0 — Adaptive Query Execution (AQE), Dynamic Partition Pruning (DPP), Pandas UDF v2.
  • 2022–2024: Spark 3.3–3.5 — Spark Connect (client-server decoupling), ANSI SQL compliance, Kubernetes maturity.

2.3 Hadoop MapReduce Limitations

Spark was created to address fundamental limitations of Hadoop MapReduce:

  • Rigid model: Every job must fit a Map → Shuffle → Reduce pipeline. Multi-step workflows require chaining independent MR jobs.
  • Disk I/O amplification: Every intermediate result is written to HDFS, causing massive disk I/O. A 5-stage pipeline reads and writes to HDFS 5 times.
  • No iterative support: ML algorithms that require many passes over data re-read HDFS each iteration.
  • Verbose API: Java-only Mapper/Reducer classes with hundreds of lines of boilerplate per job.
  • High latency: JVM startup, HDFS I/O, and YARN container allocation make interactive queries impractical.
  • Fragmented ecosystem: Separate systems for SQL (Hive), streaming (Storm), ML (Mahout), graph (Giraph).

2.5 The Spark Ecosystem

2.5.1 Spark Core

The foundation layer providing task scheduling, memory management, fault tolerance, and I/O. The RDD API is the original low-level abstraction. The BlockManager handles distributed caching and storage. All higher-level libraries compile down to Spark Core operations.

2.5.2 Spark SQL

Structured data processing using DataFrames and Datasets. Full ANSI SQL support with HiveQL compatibility. The Catalyst optimizer provides rule-based and cost-based query optimization. The Tungsten engine provides a binary memory format and whole-stage code generation for maximum CPU efficiency.

2.5.3 Structured Streaming

Stream processing using the same DataFrame API as batch — write once, run as batch or streaming. Supports micro-batch (default, seconds latency) and continuous processing modes. Native connectors for Kafka, Kinesis, and file systems. Stateful operations (aggregations, joins, deduplication) with exactly-once guarantees.

2.5.4 MLlib

Distributed machine learning library with ML Pipelines API (Transformer → Estimator → Pipeline). Includes classification, regression, clustering, collaborative filtering, and feature engineering tools. Deep integration with pandas via Apache Arrow for pandas UDFs and Spark ↔ pandas DataFrame conversion.

2.5.5 GraphX

Graph-parallel computation on top of the RDD API. Supports property graphs with built-in algorithms (PageRank, Triangle Counting, Connected Components, Shortest Paths). Includes a Pregel API for iterative graph algorithms. Note: largely superseded by the GraphFrames library in modern usage.

2.6 Why Spark Became Dominant

Unification (one engine for all workloads), speed (in-memory model), developer experience (Python-first ecosystem), cloud-native integrations (AWS EMR, Databricks, GCP Dataproc), community (largest open-source big data project with 1,000+ contributors), and commercial backing (Databricks drives rapid innovation) all contributed to Spark's dominance.

Part 3 Spark Architecture Deep Dive

Section 3 — Spark Architecture Deep Dive

3.1 High-Level Architecture

3.2 The Driver — Brain of a Spark Application

The Driver is a single JVM process hosting the SparkSession/SparkContext. It is the central coordinator for the entire Spark application. Its responsibilities include:

  • Parsing user code and building the logical plan (DAG of transformations)
  • Running the Catalyst optimizer to produce an optimized physical plan
  • Constructing the DAG of stages and individual tasks
  • Scheduling tasks to executors via the Task Scheduler
  • Tracking executor health through heartbeat monitoring
  • Collecting results from executors and returning them to the user
⚠️ Common Pitfall Driver failure = total application failure. In client mode, if the client machine dies (laptop closes, SSH disconnects), the Driver is gone and the entire job fails — all executors are killed. For production batch jobs, always use cluster mode where the Driver runs inside the cluster, surviving client disconnection.

3.3 Executors — The Workhorses

Executors are long-lived JVM processes launched on worker nodes when the application starts. Each executor:

  • Runs tasks assigned by the Driver in parallel thread slots (one task per core)
  • Stores cached RDD/DataFrame partitions via its local BlockManager
  • Writes shuffle data to local disk and serves it to other executors
  • Sends heartbeats and task results back to the Driver

The number of concurrent tasks per executor is controlled by spark.executor.cores (typically 4–5). The recommended sweet spot is 4–5 cores per executor because: (1) the JVM's HDFS client supports ~5 concurrent connections efficiently, (2) GC pause times increase with heap size, and (3) too many cores per executor means all tasks share one heap — a single bad task can GC-pressure all siblings.

With Dynamic Allocation enabled, executors can be added or removed at runtime based on pending task backlog, allowing the cluster to scale with workload.

3.4 Cluster Manager — Resource Negotiation Layer

The Cluster Manager sits between the Driver and Worker Nodes, allocating containers, monitoring node health, and enforcing resource quotas. Spark is cluster-manager-agnostic via a pluggable interface.

3.4.1 Spark Standalone

Spark's built-in cluster manager with a Master + Worker process per node. Simple setup, minimal dependencies. Good for dedicated Spark-only clusters. Limited multi-tenancy.

3.4.2 YARN (Yet Another Resource Negotiator)

Hadoop's resource manager — the industry standard for on-premise deployments. Features ResourceManager (global), NodeManagers (per node), and an ApplicationMaster (per app). The ApplicationMaster negotiates executor containers with the ResourceManager. Supports multi-tenancy via queues and capacity scheduler.

3.4.3 Kubernetes

The preferred choice for cloud-native deployments. The Driver runs as a K8s Pod; executors are dynamically launched as Pods. Production-ready from Spark 3.1+. Benefits: fine-grained resource isolation, auto-scaling, namespace quotas, and infrastructure-as-code deployment.

Section 6 — Lazy Evaluation

6.1 The Lazy Execution Model

Spark does not execute transformations when they are called. Instead, each transformation is recorded as a node in a logical plan (DAG). Execution only occurs when an action is invoked. This is fundamentally different from eager-execution frameworks (pandas, Python, SQL databases that execute each statement immediately).

6.2 Transformations vs Actions

Transformations (Lazy)TypeActions (Eager)Returns
filter() / where()Narrowshow()Prints rows to console
select() / withColumn()Narrowcount()Long (row count)
map() / flatMap()Narrowcollect()Array[Row] to Driver
union()Narrowtake(n)First N rows to Driver
groupBy() + agg()Widewrite.save()Writes to storage
join()Wideforeach()Applies func per row
repartition()Widereduce()Aggregated single value
distinct() / orderBy()Widefirst() / head()Single Row
⚠️ Common Pitfall collect() pulls all data to the Driver JVM. On large datasets, this causes Driver OOM and crashes your entire application. Always use write() for large results, or take(N)/show(N) for sampling.

6.3 How Lazy Evaluation Improves Performance

By deferring execution, Spark can inspect the entire computation plan before running anything. The Catalyst optimizer uses this to:

  • Predicate pushdown: Move filter conditions closer to the data source, reducing data read.
  • Projection pruning: Read only the columns actually needed downstream.
  • Pipeline fusion: Merge multiple narrow transformations into a single stage (single pass over data).
  • Constant folding: Evaluate constant expressions at plan time (1 + 2 → 3).
  • Join reordering: Choose the optimal join order based on table sizes.
PySpark 
# Nothing executes until .show()
df = spark.read.parquet("s3://bucket/events/")     # Lazy — no data read
df2 = df.filter("event_type = 'click'")             # Lazy — added to plan
df3 = df2.select("user_id", "timestamp", "page")   # Lazy — column pruning hint
df4 = df3.groupBy("user_id").count()               # Lazy — shuffle planned

# Catalyst sees: "I only need user_id, timestamp, page columns
# where event_type='click', then groupBy user_id"
# → Pushes filter to Parquet scan, reads only 3 columns

df4.show()  # ← THIS triggers the entire optimized pipeline

Section 8 — DAG Scheduler

8.1 Role of the DAG Scheduler

The DAG Scheduler translates the physical plan into a graph of Stages. Each stage boundary is defined by a shuffle dependency (wide transformation). The DAG Scheduler determines which stages must complete before others can start, submits stages to the Task Scheduler, and re-submits failed stages on executor failure.

8.2 Stage Boundaries — Narrow vs Wide Dependencies

⚙️ Engineering Insight The default spark.sql.shuffle.partitions=200 is a common bottleneck. For large datasets (TBs), use 400–2000. For small datasets (MBs), use 10–50. Spark 3.0 AQE can auto-tune this at runtime via spark.sql.adaptive.coalescePartitions.enabled=true — it merges small post-shuffle partitions automatically.

Section 9 — Task Scheduler

9.1 Role of the Task Scheduler

The Task Scheduler receives TaskSets from the DAG Scheduler (one TaskSet per stage) and assigns individual tasks to available executor slots. It tracks task completion, retries failed tasks (default 4 attempts via spark.task.maxFailures=4), and enforces data locality preferences.

9.2 Locality-Aware Scheduling

The Task Scheduler implements a locality-preferring delay scheduling algorithm. When a task is ready to run, the scheduler checks if a slot is available at the task's preferred locality level. If not, it waits up to spark.locality.wait (default 3 seconds) before relaxing to the next level.

9.3 Scheduling Modes

FIFO (default): Jobs submitted first get all resources until they finish. Simple but can starve later jobs.

FAIR: Resources shared equally among concurrent jobs using weighted scheduling pools. Configured via spark.scheduler.mode=FAIR and a fairscheduler.xml pool definition. Essential in multi-tenant notebook environments.

9.4 Speculative Execution

If a task runs significantly slower than its peers (default: 1.5x the median after 75% of tasks complete), Spark launches a duplicate copy on a different executor. The first to finish wins; the other is killed.

⚠️ Common Pitfall Speculative execution can cause duplicate writes for non-idempotent sinks (e.g., appending to a database without deduplication). Only enable (spark.speculation=true) with idempotent output operations or transactional sinks (Delta Lake, Iceberg). Streaming jobs should generally disable speculation.

Section 10 — RDD Internals

10.1 What Is an RDD?

Resilient Distributed Dataset is the foundational abstraction in Spark Core. RDDs are:

  • Immutable: Once created, cannot be modified — transformations create new RDDs.
  • Distributed: Partitioned across executor nodes — each partition is a chunk of data processed by one task.
  • Resilient: Fault-tolerant via lineage graph — lost partitions can be recomputed from their parents.
  • Typed at runtime: No schema enforcement — just a collection of JVM objects.

10.2 RDD Five Core Properties

Every RDD internally carries five defining properties:

  1. Partitions list: The set of partitions (data chunks) making up the dataset.
  2. Compute function: A function applied to a partition iterator to produce data.
  3. Dependencies: List of parent RDDs with dependency type (narrow or wide).
  4. Partitioner (optional): For key-value RDDs — defines how data is partitioned (hash/range).
  5. Preferred locations (optional): Data locality hints for the Task Scheduler.

10.5 Fault Tolerance via Lineage

When a partition is lost (executor crash), Spark traces the lineage DAG backwards to find the nearest available data (either source files or a checkpoint) and recomputes only the lost partition. For narrow dependencies, this recomputes just one parent partition. For wide dependencies, the entire parent stage may need to re-execute (since the lost partition depends on all parent partitions via shuffle).

For long-running iterative algorithms (ML), lineage graphs grow very deep. Checkpointing truncates the lineage by materializing the RDD to HDFS/S3: rdd.checkpoint() followed by an action to trigger the materialization.

PySpark 
# RDD API example — lineage demonstration
rdd = sc.textFile("s3://bucket/logs/")           # HadoopRDD
rdd2 = rdd.filter(lambda x: "ERROR" in x)        # FilteredRDD (narrow)
rdd3 = rdd2.map(lambda x: (x.split()[0], 1))     # MappedRDD (narrow)
rdd4 = rdd3.reduceByKey(lambda a, b: a + b)      # ShuffledRDD (wide)
result = rdd4.collect()  # Action — triggers execution

# View the lineage graph
print(rdd4.toDebugString().decode())
# Output:
# (200) PythonRDD[4] at collect
#  |   MapPartitionsRDD[3] at reduceByKey ← ShuffledRDD
#  |   ShuffledRDD[2] at reduceByKey
#  +-(2) PythonRDD[1] at map
#     |  s3://bucket/logs/ HadoopRDD[0]
⚙️ Engineering Insight Prefer DataFrame/Dataset API over raw RDDs in Spark 2+. DataFrames go through the Catalyst optimizer and Tungsten engine — getting automatic predicate pushdown, column pruning, and whole-stage code generation. RDDs bypass all of this. Use RDDs only for unstructured data, custom serialization, or when you need fine-grained partition-level control that the DataFrame API doesn't expose.

Part 5 DataFrames, Datasets & Spark SQL Engine

Section 11 — DataFrames and Datasets

11.1 The Three Structured APIs

11.2 RDD — Low-Level API (Spark 1.x)

A distributed collection of JVM objects partitioned across executors. No schema, no query optimization. Type-checked at runtime only. Verbose API with no built-in SQL support. The RDD API gives you maximum control over partitioning and per-element operations but bypasses Catalyst and Tungsten entirely, meaning identical logic written as RDD code runs 2–10x slower than the equivalent DataFrame code.

Use RDDs only when: working with unstructured data (binary, custom formats), needing custom serialization, or requiring fine-grained partition-level control not exposed by the DataFrame API.

11.3 DataFrame — High-Level API (Spark 2.x+)

A distributed collection of Row objects with a named, typed schema — conceptually identical to a SQL table or pandas DataFrame, but distributed across a cluster. DataFrames go through Catalyst optimizer and Tungsten engine, getting automatic predicate pushdown, column pruning, join reordering, and whole-stage code generation.

Crucially, DataFrames are language-agnostic in performance: the same DataFrame code in Python, Scala, Java, or R produces identical optimized physical plans. This is because the optimization happens on the logical plan, not on user code.

PySpark 
from pyspark.sql import functions as F

df = spark.read.parquet("s3://bucket/sales/")

result = df \
    .filter(df.year == 2024) \
    .groupBy("region", "product") \
    .agg(
        F.sum("revenue").alias("total_revenue"),
        F.count("*").alias("order_count")
    ) \
    .orderBy(F.desc("total_revenue"))

result.show(20, truncate=False)
result.explain("extended")  # Inspect all Catalyst plan stages

11.4 Dataset — Type-Safe API (Scala/Java Only)

Datasets extend DataFrames with compile-time type safety. They map to user-defined JVM classes (case classes in Scala). Encoders convert between JVM objects and Spark's internal binary format, giving you Catalyst optimization plus compile-time error checking. Internally, a DataFrame in Scala is Dataset[Row].

Scala 
// Define a case class with strong types
case class Order(orderId: String, customerId: String, amount: Double, status: String)

val ordersDS: Dataset[Order] = spark.read
  .parquet("s3://bucket/orders/")
  .as[Order]  // Convert DataFrame → Dataset[Order] via implicit Encoder

val highValue: Dataset[Order] = ordersDS
  .filter(_.amount > 1000.0)       // Compile-time checked lambda
  .filter(_.status == "completed")  // IDE auto-complete works on fields

// Typo like _.amoun would fail at COMPILE TIME, not runtime
highValue.show()

Section 13 — Catalyst Optimizer

13.1 Architecture Overview

13.2 Rule-Based Optimization (RBO)

Catalyst applies a fixed set of deterministic rewrite rules in multiple passes until a fixed point is reached (no more rules apply). Rules are organized into batches, each batch runs repeatedly until the plan stops changing. Key rules:

RuleWhat It DoesImpact
Predicate PushdownMoves filter conditions as close to data source as possibleReduces data read from storage by 10–1000x
Column PruningEliminates columns not referenced downstreamReads only needed columns from Parquet/ORC
Constant FoldingEvaluates constant expressions at plan timeRemoves runtime computation
Boolean Simplificationx AND TRUE → x, x OR FALSE → xSimplifies filter predicates
Join ReorderingReorders multi-way joins smallest-firstReduces intermediate result size
Subquery FlatteningConverts correlated subqueries to joinsEnables parallel execution
Limit PushdownPushes LIMIT through unions and projectionsReduces data processed upstream

13.3 Cost-Based Optimization (CBO)

CBO requires column-level statistics: row count, min/max, number of distinct values (NDV), null count, and optionally histograms. These are collected via ANALYZE TABLE and stored in the catalog:

SQL 
-- Collect table and column statistics for CBO
ANALYZE TABLE orders COMPUTE STATISTICS FOR ALL COLUMNS;

-- Verify statistics are collected
DESCRIBE EXTENDED orders customer_id;

CBO uses these statistics to: select join strategy (broadcast vs sort-merge based on actual table size), determine optimal join order in multi-way joins, and estimate filter selectivity. Enable with spark.sql.cbo.enabled=true (default true in Spark 3.x).

⚙️ Engineering Insight Stale statistics are a silent performance killer. After major ETL writes, always re-analyze tables. Delta Lake and Iceberg maintain file-level statistics automatically, reducing the need for manual ANALYZE TABLE. But for Hive-managed tables on Parquet, statistics must be collected manually.

Section 14 — Tungsten Execution Engine

14.1 Why Tungsten Was Needed

Pre-Tungsten Spark was bottlenecked by JVM overhead. Java objects are memory-inefficient: a simple String "hello" takes ~48 bytes in JVM heap (12-byte header + 16-byte char array header + 10 bytes data + padding) vs 5 bytes in raw format. Object graphs cause pointer-chasing, destroying CPU cache locality. GC pauses on large heaps (>20 GB) would stall the entire executor for seconds.

Tungsten addressed three bottlenecks: memory efficiency (binary format), GC pressure (off-heap storage), and CPU utilization (whole-stage code generation).

14.2 Binary Memory Format (UnsafeRow)

Tungsten stores data in a compact binary row format called UnsafeRow. Fixed-width fields (int, long, double) are stored inline. Variable-width fields (strings, arrays) use offset pointers. No Java object headers, no GC tracking — just raw bytes. This format is CPU cache-friendly: sequential memory access patterns maximize L1/L2 cache hits.

14.3 Off-Heap Memory Management

Spark manages memory directly via sun.misc.Unsafe — bypassing JVM GC entirely. Memory pages are allocated outside the JVM heap. Tungsten controls the full lifecycle: allocate, use, free. Configuration:

Config 
spark.memory.offHeap.enabled=true      # Enable Tungsten off-heap
spark.memory.offHeap.size=8g          # Off-heap memory size
# Total executor memory = spark.executor.memory (heap)
#                       + spark.executor.memoryOverhead (Python, Netty)
#                       + spark.memory.offHeap.size (Tungsten)

14.4 Whole-Stage Code Generation (WSCG)

Traditional query engines use the Volcano iterator model: each operator (filter, project, aggregate) calls next() on the operator below it, one row at a time. This creates massive virtual function dispatch overhead — millions of next() calls per partition, each crossing a virtual method boundary.

Tungsten's WSCG generates JVM bytecode that fuses an entire stage pipeline into a single tight loop. All operators (filter, project, aggregate) are inlined into one method — no virtual dispatch, no iterator overhead.

14.5 Verifying WSCG Is Active

PySpark 
df.explain()
# Look for *(N) prefix in the physical plan:
# *(1) HashAggregate(keys=[customer_id], ...)
#   +- *(1) FileScan parquet [customer_id, amount] ...
#
# The *(1) means "whole-stage codegen pipeline #1"
# — all operators with the same number are fused into one loop
# If you see NO asterisk → codegen is disabled or unsupported for that op
⚙️ Engineering Insight Tungsten WSCG is most impactful for CPU-bound queries: large aggregations, sort-merge joins, and wide tables with many columns. For I/O-bound queries (reading terabytes from S3), the bottleneck is network/disk, and WSCG provides minimal benefit. Focus optimization efforts on the actual bottleneck — use the Spark UI to determine whether tasks are CPU-bound (short I/O, long compute) or I/O-bound (long I/O wait).
Part 6 Shuffle System, Block Manager & Memory Management

Section 15 — Shuffle System

15.1 What Is a Shuffle?

A shuffle is the redistribution of data across partitions and executor nodes. It is triggered by wide transformations: groupBy, join, repartition, distinct, sortBy. Shuffle is the single most expensive operation in Spark because it involves disk I/O, serialization, network transfer, and deserialization — all at once.

15.2 Sort-Based Shuffle (Default)

Since Spark 1.2, the default shuffle implementation is sort-based. Each mapper task sorts its output by partition ID, writes one data file + one index file per task. The ExternalSorter spills to disk when memory exceeds threshold. This design produces 2 × M files (M = number of mappers), far fewer than the old hash-based shuffle which created M × R files (M mappers × R reducers).

15.3 External Shuffle Service (ESS)

A standalone service running on each worker node, outside executor JVMs. It serves shuffle files to reducers even after executors are killed. Required for Dynamic Allocation: without ESS, killing an executor would destroy its shuffle files, forcing upstream stages to re-execute.

⚙️ Engineering Insight Minimizing shuffles is the #1 performance optimization in Spark. Techniques: (1) Broadcast joins — eliminate join shuffle for small tables. (2) Pre-partition data at write time (bucketing). (3) Repartition once before multiple downstream operations. (4) AQE coalesce — let Spark merge tiny post-shuffle partitions. (5) Filter aggressively before joins and aggregations to reduce data entering the shuffle.

Section 16 — Block Manager

16.1 Architecture Overview

16.2 Block Types

Every unit of data in Spark is stored as a Block, identified by a BlockId. Block types include:

  • RDD/DataFrame partition blocks: rdd_5_3 = RDD 5, partition 3. Created by caching operations.
  • Shuffle blocks: shuffle_2_0_3 = shuffle 2, map task 0, reduce partition 3. Written during shuffle write.
  • Broadcast blocks: broadcast_7 = broadcast variable 7. Distributed to all executors.
  • Streaming blocks: Micro-batch data blocks for Structured Streaming.

16.3 Storage Hierarchy

MemoryStore is the first-tier storage within BlockManager. It supports three storage formats: DeserializedValues (JVM objects — fastest access, highest memory/GC cost), SerializedByteBuffer (compact bytes — lower memory, slower access), and ColumnarBatch (Tungsten columnar binary format for cached DataFrames). When MemoryStore is full, LRU eviction either drops blocks or spills them to DiskStore (local disk).

DiskStore stores blocks on the executor's local file system, configured via spark.local.dir. Using multiple paths across different physical disks improves I/O parallelism for shuffle spill.

Section 17 — Memory Management

17.1 Unified Memory Manager

17.2 Unified Memory Model (Spark 1.6+)

Before Spark 1.6, Execution and Storage memory had a hard boundary: wasted memory on one side couldn't be used by the other. The Unified Memory Manager introduced a dynamic, borrowable boundary:

  • If Execution needs more memory and Storage has idle capacity → Execution borrows from Storage.
  • If Storage needs more and Execution is idle → Storage borrows from Execution.
  • If Execution needs memory back and Storage is using it → Execution evicts cached blocks from Storage.
  • spark.memory.storageFraction=0.5 defines the minimum fraction reserved for Storage below which Execution cannot evict.

17.3 Memory Configuration Reference

Config 
# JVM Heap per executor
spark.executor.memory=16g

# Off-heap overhead (Python workers, Netty, native libs)
# Default: max(384MB, 0.10 × executor.memory)
spark.executor.memoryOverhead=4g

# Tungsten off-heap memory (outside JVM GC)
spark.memory.offHeap.enabled=true
spark.memory.offHeap.size=8g

# Unified memory fraction (default 0.6)
spark.memory.fraction=0.6

# Storage fraction within unified pool (default 0.5)
spark.memory.storageFraction=0.5

# Driver memory
spark.driver.memory=8g
spark.driver.maxResultSize=4g  # Max collect() result size

# Total per executor ≈ executor.memory + memoryOverhead + offHeap.size
# = 16g + 4g + 8g = 28g container request to YARN/K8s

17.4 GC Tuning

For executors with heap >16 GB, use G1GC: add -XX:+UseG1GC to spark.executor.extraJavaOptions. Monitor GC via Spark UI → Executors tab: if GC time / Task time > 10%, you have a GC problem. Mitigations: increase off-heap usage (Tungsten), reduce cached data, or increase executor count (smaller heaps per executor).

⚠️ Common Pitfall spark.executor.memoryOverhead is often forgotten. Python UDFs, Arrow batches, and Netty all consume off-heap memory outside the JVM heap. If you only set spark.executor.memory, the YARN or K8s container is slightly larger than your heap — and Python/Netty quickly exceed the container limit. Result: "Container killed by the YARN NodeManager" — not a Java OOM, but a container-level OOM kill. Always set memoryOverhead explicitly for PySpark workloads.

Section 18 — Executor Out of Memory (OOM)

18.1 Types of OOM in Spark

OOM TypeError Message / SymptomRoot Cause
Heap OOMjava.lang.OutOfMemoryError: Java heap spaceToo much data in execution/storage memory
Off-heap OOMContainer killed by YARN/K8s (no Java exception)Python workers / Netty / native libs exceed memoryOverhead

Metaspace OOMOutOfMemoryError: MetaspaceToo many generated classes (WSCG, UDFs) — rare

18.2 Root Causes and Fixes

Large Partitions

Too few partitions → each task processes too much data → single task OOM. Fix: increase spark.sql.shuffle.partitions, call repartition(N) before heavy operations. Target: 100–400 MB of data per partition.

Data Skew

One or a few partitions hold dramatically more data than others. One executor OOMs while others are idle. Fix: salting, AQE skew join, custom partitioner (see Section 21).

Inefficient Joins

Sort-merge join on skewed keys builds large in-memory buffers. Joining a large table with itself without filtering. Fix: filter before join, use broadcast join for small tables, increase memory.

Caching Too Much Data

Caching large DataFrames without enough storage memory → storage steals from execution → execution OOMs during shuffle. Fix: df.unpersist() after use, use MEMORY_AND_DISK storage level, cache only what you reuse.

18.3 Debugging OOM Step by Step

  .orderBy(F.desc("count")).show(20)
# If top few keys have >> average rows → skew on that key

# Step 3: Inspect execution plan for surprises
df.explain("extended")
# Look for: CartesianProduct, BroadcastNestedLoopJoin, missing pushdowns

# Step 4: Enable AQE (handles many OOM causes automatically)
spark.conf.set("spark.sql.adaptive.enabled", "true")

# Step 5: Check Spark UI

# → Stages tab: input size, shuffle write, task duration outliers

(3) Diagnose root cause: skew, large partitions, caching, or bad join. (4) Apply targeted fix: repartition, salt, broadcast, unpersist. Don't jump straight to "increase memory" — that treats the symptom, not the cause.

19.2 Repartition vs Coalesce

PySpark 
# Repartition: full shuffle, balanced output, can increase or decrease
df_repartitioned = df.repartition(200, "customer_id")
# Hash-partitioned by customer_id — same customer always in same partition
# Use before joins on customer_id (co-partitioned = faster join)

# Coalesce: NO shuffle, fast, decrease only
df_coalesced = df.coalesce(10)
# Merges adjacent partitions locally — use before final write to reduce file count
# WARNING: can produce unequal partition sizes if input is skewed

# Common pattern: large pipeline → repartition for parallelism → coalesce for output
df.repartition(200, "customer_id") \
  .groupBy("customer_id").agg(F.sum("amount")) \
  .coalesce(50) \
  .write.parquet("s3://bucket/output/")

19.3 Partition Pruning (Static)

When reading Parquet/ORC data partitioned on disk (e.g., /data/year=2024/month=12/), Spark's file source reader skips entire directories that don't match filter predicates. This is static partition pruning — the pruning happens at plan time based on literal values in the WHERE clause. Dynamic Partition Pruning (Section 25) extends this to runtime-determined values from dimension table joins.

Section 20 — Join Strategies

20.1 Overview of Join Strategies

20.2 Broadcast Hash Join (BHJ) — The Performance Winner

BHJ broadcasts the smaller table to all executors as an in-memory HashMap. Each executor performs a local hash lookup against its partitions of the large table — zero shuffle on the large table. This is the fastest join strategy by far.

PySpark 
from pyspark.sql.functions import broadcast

# Automatic broadcast: if small_products < autoBroadcastJoinThreshold
result = large_orders.join(small_products, "product_id")

# Explicit broadcast hint (overrides threshold check)
result = large_orders.join(
    broadcast(small_products),
    on="product_id",
    how="inner"
)

# Increase threshold to 256 MB for star-schema workloads
spark.conf.set("spark.sql.autoBroadcastJoinThreshold",
               str(256 * 1024 * 1024))
⚙️ Engineering Insight Setting spark.sql.autoBroadcastJoinThreshold=268435456 (256 MB) is one of the highest-impact Spark configs for star-schema analytics. If your dimension tables fit in 256 MB, every fact-dimension join becomes a broadcast hash join — eliminating the shuffle entirely. This single config change often cuts ETL wall-clock time by 50–70%.

20.3 Sort Merge Join (SMJ) — Default for Large Tables

Both tables are shuffled by join key, then sorted, then merged in a streaming fashion. Memory-efficient because it processes data sequentially without building a full hash table. The default for large × large joins when neither side fits in broadcast threshold. Downside: double shuffle + sort is expensive.

20.4 Join Selection Decision Tree

20.5 Cartesian / Broadcast Nested Loop Join — Last Resort

When no equi-join condition exists (e.g., ON a.x > b.y), Spark falls back to a cross product. M × N rows — exponentially expensive. The plan will show CartesianProduct or BroadcastNestedLoopJoin. Always check explain() for these — they usually indicate a missing or incorrect join condition in your query.

⚠️ Common Pitfall A missing join key in a multi-table SQL query silently produces a cross join. Spark will not error — it will attempt to compute M × N rows, typically causing OOM or running for hours. Always verify your join conditions in the physical plan via df.explain(). Look for CartesianProduct or BroadcastNestedLoopJoin as red flags.
